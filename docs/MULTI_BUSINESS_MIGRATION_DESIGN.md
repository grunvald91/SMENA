# Миграция ServGo Смена к полноценной модели нескольких бизнесов

**Статус:** дизайн обязательной миграции и release gates, **не выполнено в Telegram Serverless**. Ниже перечислены технические проверки, а не факт, что backup/restore уже доступны на платформе.

## Почему не снимаем ограничение сразу

Сейчас `organizations.owner_tg_id` в существующей базе — `NOT NULL UNIQUE`. Поэтому новая таблица членства и интерфейс выбора уже поддерживают несколько доступных организаций (например, владелец одного бизнеса и управляющий другого), но не позволяют одному человеку создать второй собственный бизнес. Для удаления ограничений потребуется перестройка таблицы SQLite: простое изменение JavaScript-схемы может породить небезопасную миграцию.

До этого исходные legacy owner-only функции получают организацию по owner_tg_id. **Нельзя** молча переключить эти методы на выбранный orgId: это ошибка tenant isolation. Промежуточный security guard `scoped-owner.js` блокирует управление, если выбор не совпадает с исходным бизнесом. Внесён в `requireOwner`, `getContext` и `controlContext`.

## План миграции

1. Снять полный read-only inventory реальной базы: количество организаций, сотрудников, назначений, устройств, смен, фотоконтролей, бонусов и журналов. Сохранить контрольную сумму схемы.
2. Проверить предоставляемые Telegram Serverless способы резервного копирования и восстановления; выполнить **реальное** восстановление в изолированном тестовом контуре. Если такого способа нет, не запускать изменение существующей таблицы на production.
3. Убедиться, что все существующие владельцы получили membership `role=owner,status=active`. Историческое поле owner_tg_id остаётся совместимым на этапе перехода.
4. Новая целевая модель: `organizations` без уникального ограничения по owner_tg_id, `organization_memberships` с уникальностью по паре org_id/user_tg_id; действующие org.id сохраняются. При пересоздании таблицы — перенос всех записей в транзакции, проверка количества и целостности связей.
5. Поднять сервисные функции на явный `orgId` + централизованную проверку разрешений; обновить все /report, /team, /employee, /shiftadd, /shiftassign, /bind, Mini App endpoints, фотоконтроль, устройство и audit. Исправить серверную авторизацию, не только кнопки.
6. Тесты матрицы: владелец A/B, управляющий B, сотрудник B, уволенный из B, владелец и сотрудник в разных организациях; повторная команда с чужим ID; два одинаковых имени бизнеса; ночные и параллельные смены.
7. Canary на тестовом боте, затем отдельно подтверждённый production deploy с `tgcloud migrate --dry-run --local`. Не выполнять destructive migration через `--force` или без проверенного backup/rollback.

## Границы ролей и данных

- `owner`: полный доступ к своей организации, ролям и предварительным начислениям.
- `manager`: только предоставленные владельцем кадровые/операционные права, но не ставки и зарплаты по умолчанию.
- `employee`: собственные смены и собственные задания.
- Пользователь не может менять `orgId` в запросе ради получения доступа. Каждая запись `employeeId/locationId/templateId/shiftId` проверяется в выбранной организации.
- Для привязки рабочего чата требуется роль владельца или специальное полномочие + Telegram administrator и действующие права бота публиковать фото.
- Публичный рабочий экран не имеет камеры и не зависит от сетевого соединения с сервером ServGo.
